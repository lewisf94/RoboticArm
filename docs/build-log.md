## 2026-07-19 — T23: ROS 2 arm_description (URDF + RViz)

- New `ros2/arm_description` package: `bench_arm.urdf.xacro` (base yaw + shoulder pitch, revolute; forearm rigid via a `fixed` elbow_fixed joint since the bench rig has no elbow servo; grip jaw revolute, decorative), `launch/view.launch.py` (robot_state_publisher + joint_state_publisher_gui + rviz2), `rviz/arm.rviz`, README. Geometry constants (base_h/L1/L2, joint limits) copied from `bench_3dof.h` with source comments, converted mm→m and deg→rad only inside the xacro (`${.../1000}`, `${radians(...)}`).
- No ROS 2 install exists in this sandbox and CLAUDE.md forbids trying (`colcon`/`apt-ros` are CI/host-only) — the usual "trust the toolchain" gap from the ESP32 tasks, except this time there's no equivalent to the Arduino-stub trick, since URDF isn't compiled code. Closed as much of that gap as practical: `pip install xacro` (a genuinely standalone package, no ROS runtime needed) to actually expand the macros rather than eyeball them; `pip install urdfdom-py` (the same parsing library `check_urdf` is built on) to structurally validate the expanded URDF — single root, no duplicate/cyclic parentage, unique names; and an independent Python script composing the joint-chain rotation matrices to check the FK against the task's required golden vector.
- That FK check caught the one thing worth catching by hand-derivation alone: the shoulder joint's rotation axis. A plain rotation about +Y sends the arm from horizontal *downward*; getting "0°=horizontal, positive=up" (docs/kinematics.md's q1 convention) requires axis `0 -1 0`, not `0 1 0`. Verified by direct rotation-matrix computation (not just asserted) before writing it into the file, then independently re-derived via the script: zero pose lands the tool at exactly (0.260, 0.000, 0.060) m as required, and two extra sanity checks (shoulder at 90° → straight up at (0,0,0.32); base at 90° with shoulder at 0 → tool swings to +Y) both came out matching the geometry by hand.
- Added a `ros2` CI job (`ros:jazzy-ros-base` container): `colcon build` then `xacro` + `check_urdf`. Included `python3-colcon-common-extensions` beyond what the task named explicitly — colcon itself isn't guaranteed present in the `ros-base` image variant, and without it the build step the task asks for can't run at all.
- Verified: `pio test -e native` unaffected (46/46, this task never touches C++/PlatformIO). URDF verified via the xacro+urdfdom-py+FK pipeline above. **Not verified: CI `ros2` job (will check after push) and the RViz/slider acceptance item — no ROS 2 environment in this session.**

- Firmware: trims load from NVS at boot and persist on `set_trim` (`Preferences`, namespace `arm`, key `trim<j>`); debounced (20 ms) e-stop input on GPIO 10 — open acts exactly like the `estop` command, re-closing clears the inhibit but stays disabled until an explicit `enable`; WS2812 status LED (red disabled / green enabled / blue blink latched), written only on color change; 10 Hz `state` lines while streaming; heap reported via `ESP.getFreeHeap()`.

## 2026-07-18 — T04: LEDC servo HAL + firmware shell (M1 hardware gate)

- Added `IJointOutput` (`lib/arm_core`), `LedcServoOutput` (`lib/arm_hal`, arduino-esp32 2.0.17's channel-based LEDC API: `ledcSetup`/`ledcAttachPin`/`ledcWrite`/`ledcDetachPin` — confirmed via web search that `platform = espressif32@^6.12.0` maps to core 2.0.17, *not* the pin-centric `ledcAttach` API core 3.x replaced it with, since those have incompatible signatures), `src/pins.h`, and rewrote `src/main.cpp` into the real firmware shell: global `MotionController`/`LedcServoOutput`/`Protocol`, boot disabled/detached, `hello` line, non-blocking serial reader, 50 Hz `millis()`-driven tick.
- This task can't be verified the way T01-T03 were: `src/` and `lib/arm_hal/` need `Arduino.h`, so none of it builds under `pio test -e native`, and `pio run -e esp32s3` needs the PlatformIO registry, which is blocked in this sandbox (confirmed again — instant HTTPClientError). To avoid shipping ~150 lines of firmware code with *zero* verification, wrote a throwaway stub `Arduino.h` (just the handful of Serial/millis/LEDC declarations this code actually calls, typed per the confirmed 2.0.17 API) in the scratchpad and compiled `main.cpp` + `ledc_servo_output.cpp` against it with plain g++ (`-Wall -Wextra`, zero warnings). That verifies the C++ itself — types, arm_core integration, control flow — is sound; it can't verify the *real* SDK matches the stub, which is what CI's `pio run -e esp32s3` is for.
- Serial line reader discards oversized lines (>512 bytes) via an explicit overflow flag rather than just letting the buffer stop filling — without it, the tail of a too-long line would restart accumulating from index 0 and could be misread as a valid (truncated) command once its `\n` finally arrived.
- Fixed a stale doc comment while wiring `Protocol::SystemHooks` up to real global state: T03 said `ctx` is "required, never null," but `Protocol` only ever passes `ctx` *through* to a callback, never dereferences it — main.cpp's hooks read/write global `motion`/`servo_output`/`enabled` directly and have no need for it, so `ctx=nullptr` is correct here. Corrected the comment rather than threading a meaningless non-null pointer through just to satisfy it.
- `docs/architecture.md`'s Runtime Model section described a FreeRTOS timer/task for the tick and a ring buffer for commands - both anticipate T07's async WebSocket producer, which doesn't exist yet. Updated it to describe what T04 actually is (single-threaded `millis()` polling, no ring buffer needed with only one synchronous producer) and to flag that WS lands as a second producer in T07.
- Verified: `pio test -e native` (42/42, unchanged). `pio run -e esp32s3`: not run, registry blocked - delegated to CI. **(hardware)** all three T04 acceptance items (smooth move on `set_joint`, refusal on out-of-range, instant limp on `estop`) not verified - no hardware in this session.

## 2026-07-17 — T03: Protocol dispatcher in core

- Added `Protocol` (`lib/arm_core`): `handle_line()` (parse → dispatch → one reply) and `state_json()`, implementing `get_state`, `get_profile`, `enable`, `estop`, `set_joint`, `set_joints`, `jog`, `grip`, `home`, `set_trim` per `docs/protocol.md`. Firmware/NVS access goes through `SystemHooks` (plain function pointers + `void* ctx`) so the core stays framework-free.
- ArduinoJson v7 dropped `StaticJsonDocument`'s genuinely-fixed buffer (it's now `JsonDocument` + an `Allocator*`, defaulting to heap malloc/realloc/free). Wrote a small `BoundedAllocator` (malloc/realloc/free-backed, hard byte cap, 16-byte size-header per block) to get "fixed size, no unbounded heap" back, rather than hand-rolling a bump/arena allocator — delegating the actual pointer arithmetic to libc removes an entire class of buffer-management bugs for ~30 lines of code.
- Hit and fixed a real bug from this: ArduinoJson always allocates its **first** variant-pool chunk at `ARDUINOJSON_POOL_CAPACITY` slots (4096 bytes on a 64-bit host) regardless of how little a message uses, then shrinks it back down after parsing (`ARDUINOJSON_AUTO_SHRINK`). An initial 2048-byte cap refused that very first allocation, so *every* command silently produced an empty reply, including ones that should've said `bad_json`. Fixed by sizing the budget (6144 bytes) to clear that first chunk rather than the message content. Verified with a small standalone repro outside the Unity/SCons loop before touching the real file — much faster than iterating through the full test harness.
- Also verified from source (not assumed) that assigning a `const char*`/`char[]` into a `JsonDocument` always copies — only a literal `"..."` token gets zero-copy treatment. That's what makes it safe to build error messages in a handler-local `char msg[64]` and hand them to a *different* document (`out`) than the one holding the request; no dangling-pointer risk despite the two documents having separate `BoundedAllocator` instances.
- Deviations from the original protocol.md text, now folded into that doc in this commit: `get_state`'s reply is `type:"state"` directly (not wrapped in an `ack`); `get_profile`'s exact reply shape is now spelled out as JSONC; `set_joints` requires `deg` to be exactly `n_joints` long (extra/missing entries → `bad_args`, not forwarded to a lower-level error); `set_trim` requires `enable` (grouped with the other "motion commands" per the task's own framing, even though it doesn't move anything through `MotionController`).
- 18 new Unity tests in `test/test_protocol/` (reusing `kBench3Dof`, unlike T02's dedicated profile — no need for differing per-joint vmax here). `pio test -e native`: 42/42 passed, no warnings. `pio run -e esp32s3` still blocked in this sandbox — delegated to CI.

## 2026-07-16 — T02: MotionController: slew limits + synchronized eased moves

- Added `MotionController` (`lib/arm_core`): owns a fixed `JointModel[kMaxJoints]` array bound to the profile's joints, `tick()`, `move_to()` (two-pass validate-then-apply, NaN sentinel = leave joint, restarts from live `current` on retarget), `set_joint()`.
- Non-obvious finding worth flagging for future tasks: the existing cubic ease-in-out (from M0) has peak velocity = **3x** its average, so the "clamp per-tick change to vmax·dt" guard in the spec isn't a rare backstop — it binds on whichever joint sets the shared move duration on every synchronized move. `tick()` treats active (eased) and idle (direct-to-target) joints identically: compute a desired position, then clamp the step, which is what makes "no overshoot" hold unconditionally.
- `moving()` is position-based (any joint off-target beyond a 0.01° epsilon), not elapsed-time-based, so it stays true until joints have *physically* caught up even if a move's nominal duration has already elapsed under clamp-induced lag. `progress()` stays elapsed-time-based (simple 0-1 ETA indicator) — the two intentionally answer different questions.
- Proved (and used to design the "sync arrival" test) that joints with *equal* `|Δ|/vmax` ratios stay at an identical normalized position every tick regardless of clamping, so they're guaranteed to arrive on the same tick even with different deltas and different vmax.
- 11 new Unity tests in `test/test_motion/` (dedicated 3-joint profile with differing vmax, since bench_3dof's joints share vmax). `pio test -e native`: 24/24 passed, no warnings. `pio run -e esp32s3` still blocked in this sandbox — delegated to CI.
